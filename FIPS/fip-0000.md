## Abstract

The FullOn Improvement Proposal process is the canonical path for proposing, reviewing, accepting, implementing, and recording material changes to FLON. It separates technical implementation from governance approval and prevents a merged document from being mistaken for an activated protocol change.

## Scope

A FIP is required for changes that affect one or more of:

- consensus or deterministic chain execution;
- system-contract behavior or privileged permissions;
- token issuance, rewards, slashing, or other economic rules;
- block-producer election or DAO governance;
- public APIs, transaction formats, or ecosystem-wide standards;
- activation, migration, or compatibility policy.

Bug fixes that restore already-specified behavior, documentation corrections, and ordinary application features normally do not require a FIP.

## Proposal categories

- **Core**: consensus, virtual machine, intrinsic, node, or system-contract behavior.
- **Interface**: RPC, ABI, wallet, indexer, or interoperability standards.
- **Economics**: issuance, rewards, staking, voting weight, or penalties.
- **Governance**: decision rights, proposal execution, treasury, or emergency powers.
- **Meta**: the FIP process itself.
- **Informational**: non-normative guidance or architecture records.

A proposal MAY list multiple categories.

## Required document sections

Every standards-track FIP MUST contain:

1. Abstract
2. Motivation
3. Specification
4. Rationale
5. Backwards Compatibility
6. Security Considerations
7. Economic and Governance Considerations, when applicable
8. Test and Acceptance Criteria
9. Activation and Rollback
10. Reference Implementation

Material unknowns MUST be identified. Suggested parameters MUST NOT be represented as accepted parameters before simulations and governance approval are complete.

## Statuses

| Status | Meaning |
| --- | --- |
| Idea | Pre-repository discussion without a numbered specification. |
| Draft | Numbered proposal open for substantive changes. |
| Review | Specification is complete enough for formal review. |
| Last Call | Review issues are resolved; only blocking corrections remain. |
| Accepted | Specification is approved, but may not yet be implemented or activated. |
| Implemented | Compatible code exists and required tests have passed. |
| Final | Activation and post-activation acceptance criteria are verified. |
| Deferred | Work is intentionally paused. |
| Withdrawn | Authors stopped the proposal. |
| Rejected | Review or governance rejected the proposal. |
| Superseded | Another FIP replaces the proposal. |

The normal path is `Draft -> Review -> Last Call -> Accepted -> Implemented -> Final`. Every transition MUST be made by pull request and MUST link its supporting evidence.

## Numbering and files

- Maintainers assign the next available integer after initial triage.
- Proposal files use `FIPS/fip-NNNN.md`, zero-padded to four digits.
- FIP-0000 defines this process.
- Renumbering after merge SHOULD be avoided.
- Images and supporting artifacts belong in `assets/fip-NNNN/`.

## Review and acceptance

At least two maintainers MUST approve a standards-track proposal before `Last Call`. Reviewers SHOULD include expertise matching every affected category. Core or system-contract changes additionally require:

- deterministic replay or consensus analysis;
- testnet results;
- migration and rollback review;
- security review;
- confirmation that all validator software and contract dependencies are available.

Economics proposals additionally require reproducible simulations or historical-data analysis. Governance proposals require an explicit authority matrix, timelock policy, and emergency-power expiry.

`Last Call` MUST remain open for at least 14 calendar days unless an active chain-security emergency is documented. Any normative change during Last Call returns the proposal to `Review`.

Acceptance is recorded by maintainers after the review requirements are met. If on-chain governance is already authoritative for the affected domain, the corresponding proposal or referendum result MUST also be linked before status becomes `Accepted`.

## Implementation and activation

`Accepted` authorizes implementation; it does not by itself authorize activation. The status becomes `Implemented` only when the reference implementation, automated tests, testnet report, and operational runbook are linked.

Consensus changes MUST specify a coordinated activation condition such as a protocol feature, activation height, or activation time. A system-contract-only deployment MUST name the authorized account and deployment transaction. The status becomes `Final` only after activation and the FIP's post-activation checks succeed.

Emergency deployment MAY precede the normal process only to contain an active security incident. A retrospective FIP, exact deployed commit, authority approvals, and rollback record MUST be published within seven days.

## Pull request rules

- One proposal per pull request, except a process bootstrap may include FIP-0000 and the first proposal.
- The pull request title SHOULD be `FIP-NNNN: <title>`.
- Draft pull requests are encouraged for early collaboration.
- Review comments and resolutions form part of the decision record.
- Status transitions SHOULD use separate pull requests after initial publication.
- Editors MAY correct spelling or formatting without changing normative meaning.
